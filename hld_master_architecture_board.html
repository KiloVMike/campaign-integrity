The Core Invariant
active_schedule(c) ⇒ current_rev(c).state = APPROVED ∧ decision.rev_id = current_rev(c).id ∧ decision.content_hash = current_rev(c).content_hash
“The campaign that gets scheduled is the exact campaign that was approved.”

1. System Context & Roles

  • Marketer Role: Authors proposals, edits drafts, submits for review, revises after feedback, schedules approved campaigns. Strictly separated from approval permissions.
  • Reviewer Role: Inspects submitted content, signs approval bound to SHA-256 content hash, or requests changes. Strictly prohibited from approving self-authored proposals.
  • System Engine: Enforces state machine, computes hashes, executes atomic row-locked scheduling checks, and records append-only audit events.

2. Containers & Clean Architecture

  • Mobile App (React Native + Expo): UI Screens ➔ ViewModels ➔ Mobile Domain Helpers ➔ Repositories ➔ SQLite Outbox Engine.
  • API Modular Monolith (Node.js + TS): HTTP Layer (JWT/Schema validation) ➔ Application Services (Tx boundary) ➔ Domain Model (Invariants) ➔ Persistence Repositories.
  • PostgreSQL ACID Engine: Campaigns, Revisions, Decisions, Schedules, AuditEvents, and IdempotencyKeys tables.
  • Dependency Inversion: Domain core imports nothing from Express or SQL. Data layer implements domain repository ports.

3. Source of Truth Matrix

  • PostgreSQL: Sole system of record for campaigns, immutable revisions, decisions, schedules, and audit events.
  • Client SQLite: Read projection cache + intent outbox queue. Client is never authoritative.
  • Approval Eligibility: Dynamically derived from (current_revision + decision + matching_hash). Never stored as a mutable boolean flag.
  • Observability: Structured JSON logs, domain metrics, and correlation IDs for runtime diagnostics.

4. Copy-on-Write Lifecycle

  • Proposal Submission: Rev 1 created in DRAFT ➔ locked in IN_REVIEW.
  • Changes Requested: Reviewer notes feedback ➔ Marketer revises ➔ Copy-on-Write forks Rev 2 DRAFT (Rev 1 superseded).
  • Bound Approval: Reviewer approves Rev 2 ➔ Decision bound to Rev 2 ID + SHA-256 hash.
  • Single Atomic Gate: SELECT FOR UPDATE verifies revision state, hash match, and schedule uniqueness before inserting schedule.
  • Post-Approval Guard: Any edit post-approval forks Rev 3 DRAFT and atomically cancels active schedules.

5. Architectural Business Rules

  • BR-1 Eligibility Gate: Only campaigns in approved state are eligible for scheduling.
  • BR-2 Revision & Hash Bound: Decision explicitly matches revision ID and exact SHA-256 content hash.
  • BR-3 Copy-on-Write Mutation: Editing supersedes prior revision and revokes active schedule atomically.
  • BR-4 Materiality: In v1, objective, audience, channel, and budget are material; any change generates a new revision.
  • BR-5 Idempotency: Client UUID keys guarantee exactly-once execution across network retries.
  • BR-6 Separation of Duties: Author cannot review own proposal (service authorization check).

6. Scope Boundaries & Defensibility

  • In Scope: Proposals, immutable revisions, SHA-256 verification, row-locked scheduling transaction, SQLite outbox sync, append-only audit trail.
  • Honest Non-Goals: Ad publishing to third parties, creative asset CDN, billing/payments, push notification transport.
  • Crash & Network Proof: SQLite outbox with exponential backoff prevents duplicate taps and reconciles after app kill.
  • Evolvability (ADR-001): Designed for dual multi-party approvals above budget thresholds without altering core invariant.
